## 1. Bug Description

### 1.1 Summary

数据库表定义（用户端和管理端）中缺少字段注释（COMMENT），导致开发者无法快速理解字段的业务含义，增加维护成本。

### 1.2 Reproduction Steps

1. 查看 PostgreSQL 表结构或迁移 SQL 文件
2. 发现字段定义如 `id: uuid("id").primaryKey().defaultRandom()` 没有注释
3. 无法快速理解字段的业务用途和含义

### 1.3 Expected Behavior

所有数据库表字段应该有清晰的注释（COMMENT），方便：
- 新成员快速理解数据库结构
- 开发者快速定位字段用途
- 减少跨团队沟通成本
- 便于后期维护和优化

### 1.4 Actual Behavior

表定义中：
- Drizzle Schema 定义没有使用 `.comment()` 方法
- SQL 迁移脚本也没有 COMMENT 语句
- 字段仅靠变量名推断含义

## 3. Root Cause Analysis

### 3.1 Immediate Cause

Drizzle ORM 和 SQL 迁移脚本中都没有为字段添加注释（COMMENT）。

### 3.2 Root Cause

| 模式 | 具体问题 |
|--------|----------|
| **工作流设计缺陷** | Schema 定义阶段没有强制要求使用 `.comment()` 或添加 COMMENT 语句 |
| **缺失验证机制** | 没有 linting 规则或 CI 检查来确保字段注释完整性 |
| **文档标准不明确** | 项目没有制定字段注释的编码规范 |

### 3.3 Workflow-Level Cause

**为什么工作流允许这个 Bug 发生？**

1. **Schema 定义没有文档规范** — 没有要求开发者为所有字段添加 `.comment()`
2. **代码审查流程不完善** — 缺少对 Schema 定义注释的审查标准
3. **迁移脚本生成流程缺失注释检查** — 生成的 SQL 没有验证是否包含 COMMENT

## 4. Prevention Strategy

### 4.1 Workflow Change

| Current | Proposed |
|---------|----------|
| Schema 定义允许无注释 | 强制所有非技术字段必须使用 `.comment()` |
| 代码审查不检查注释 | 将字段注释完整性加入 CR 清单 |
| SQL 生成不含注释 | 重新生成迁移脚本并验证 COMMENT |

### 4.2 Automated Validation

| 验证类型 | 具体措施 |
|----------|----------|
| **静态分析** | 创建 ESLint 规则，检查 Drizzle 表定义是否使用 `.comment()` |
| **单元测试** | 测试 Drizzle 生成的 SQL 是否包含 COMMENT 语句 |
| **集成测试** | 验证 PostgreSQL 表 COMMENT 与 Drizzle 定义一致 |
| **Runtime 检查** | 不适用（此为定义阶段问题） |

## 8. Lessons Learned

1. **ORM 配置应考虑文档性** — Drizzle Schema 应该内置强制字段注释的最佳实践
2. **分阶段实施** — 先定义 Schema 规范，再批量修复现有代码
3. **验证先行** — 修改前先建立验证机制，防止遗漏
4. **文档驱动开发** — 清晰的编码规范比临时修复更有效
